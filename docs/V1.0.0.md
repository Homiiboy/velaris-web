# Velaris V1.0.0 — First Stable Release

**Status: Stabilization in progress**

V1.0.0 is the first stable Velaris release. The product scope is frozen after V0.9.0 Feature Complete; this phase focuses on compatibility, reliability, accessibility, performance and release-blocking defect removal rather than another major feature family.

## Stabilization plan

- complete cross-feature regression pass
- desktop/mobile/tablet/TV validation
- keyboard, remote and accessibility validation
- performance profiling and optimization
- error/connection-loss and permission edge cases
- migration/backward-compatibility checks for all Velaris preferences
- robust V0.x upgrade path
- broader automated regression coverage
- production build and generated-bundle ES compatibility validation
- no known release-blocking defects before finalization

## Stabilization work started

### Preference and browser-storage hardening

The first V1 stabilization batch addresses persisted client state before broader UI and performance passes.

- Discovery Watchlist/custom-list persistence is moved from a user-only V0.x key to a server+user-scoped V2 key.
- Existing V0.x Discovery data remains readable and is migrated automatically on first access for the active server/profile.
- Existing server-scoped data takes precedence over the legacy fallback after migration.
- Discovery persistence now fails safely when browser local storage is unavailable.
- Profile and Control Center preference readers now accept unavailable browser storage and fall back to supported defaults instead of relying on direct storage access.
- Profile startup/session choice handling is hardened for unavailable session storage.
- direct Local Storage / Session Storage access used by these surfaces is routed through a compatibility-safe Velaris storage helper.
- regression coverage verifies Discovery migration/scoping and unavailable-storage fallback behavior.
- the shared Velaris storage helper is included in strict zero-warning lint.

## Compatibility guarantees for the first batch

- no V0.x Discovery lists are intentionally deleted during migration
- the legacy Discovery key remains as a read fallback so failed storage writes do not destroy access to existing list data
- Control Center and Profiles retain their existing server+user key formats
- unavailable browser storage degrades to safe defaults/current in-memory state rather than preventing the app shell from rendering
- Jellyfin authentication, media permissions, playback, transcoding and server metadata remain unchanged
